# Decisions — Map the reference layer to RDF

## 1. Target graph: `…/kg/graph/reference`, not `…/kg/graph/inputs`

**Decided**, confirmed with the user. The task cited "§5" for emitting into
`…/kg/graph/inputs`, but namespaces.md §5's own named-graph table explicitly assigns
`ref_specialty`/`ref_codes`/`ref_rules` to `…/kg/graph/reference` ("build only"), separate
from `…/kg/graph/inputs` ("loader only, immutable after load", for referrals/states/
clinical/capacity). Followed the doc's own table over the task's citation, on the reasoning
that the citation was pointing at the wrong graph name rather than the doc's graph split
being silently revised.

## 2. `eatd:scheme/{code_table}` for the 7 non-CPC ConceptScheme IRIs

**Decided**, confirmed with the user. `eat:CPCScheme` is a named `eat:` vocabulary term,
hardcoded as static TBox content in `eat.ttl`/`ontology.md` §6 — not something a mapping
mints. namespaces.md §4 templates the per-row concept IRI (`{code_table}/{code_value}`,
relative to `eatd:`) but has no template for the scheme node itself for the other 7 tables.
Since a ConceptScheme grouping reference-data rows is itself reference data, not vocabulary
(per namespaces.md's own `eat:`/`eatd:` split — "never mint an instance under `eat:`"), the
scheme IRI was minted under `eatd:`: `scheme/{code_table}`, e.g. `eatd:scheme/gp_priority`.

## 3. `eat:outranks` is not regenerated by this mapping

**Decided.** The three `eat:outranks` triples (`cpc/1 outranks cpc/3, cpc/2`; `cpc/3
outranks cpc/2`) already exist as static content in `eat.ttl`, asserted directly by
`ontology.md` §6 rather than derived from any source table. Having the mapping also produce
them (e.g. via a self-join over `severity_rank`) would duplicate the same triples across the
ontology graph and the reference graph, with no consumer needing them in both places and a
real risk of the two copies drifting if one is ever hand-edited and the other isn't. The
mapping only mints the SKOS concepts (`notation`/`prefLabel`/`inScheme`) and the
`severityRank`/`crtDays` literals `ontology.md` §6 explicitly asks for.

## 4. `ontology.md` §6 undercounted the CPC scheme — corrected here

**Found, not invented.** `ontology.md` §6's worked example showed three CPC concepts
(Urgent/Semi-Urgent/Routine); `core.ref_codes` has four `triage_category` rows — code 4,
"Excluded", with `severity_rank` and `crt_days` both `NULL`. The task named this
discrepancy explicitly and asked for it to be resolved by minting code 4 as a scheme member
with no rank, no CRT days, and no `outranks` participation in either direction — done in
both the mapping (via `CPCSeverityRankMap`'s and `CPCCrtDaysMap`'s `IS NOT NULL` filters,
which naturally exclude it) and `ontology.md` §6's example (added directly, with a note
explaining the original example was short one concept).
