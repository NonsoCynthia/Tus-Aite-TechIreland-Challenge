# Ontology specification

Normative. `kg/ontology/eat.ttl` implements this file; where they disagree, this file is
the requirement and `eat.ttl` is the bug.

Currently `eat.ttl` is a five-term stub covering only `referral_state`. Completing it is
the first track, and it blocks everything else.

---

## 1. Reused vocabularies

| Vocabulary | Used for |
|---|---|
| **PROV-O** | The whole decision layer. `cites` is `prov:used`; scores, decisions, rule checks and rationales are entities generated by activities associated with versioned agents |
| **SOSA** | Observations. `sosa:Observation`, `observedProperty`, `hasSimpleResult`, `resultTime`, `hasFeatureOfInterest` |
| **OWL-Time** | Suspension intervals — required for `adjustedWaitDays` to be derivable |
| **SKOS** | Every code list in `ref_codes`, plus specialties and CPC |
| **QUDT** | Units, on the observable property |
| **SHACL** | Structural shapes and rule constraints |
| **DCAT / VoID** | Dataset metadata, release tag, seed |

**Deliberately not used.** FHIR RDF — no interop requirement in this challenge and it
would double every class; keep field names MDS-aligned so the mapping stays possible
later. The SNOMED CT ontology — licensed and enormous; reference `sct:` IRIs, import
nothing. FOAF and `org:` — no people or organisations are named in this dataset by design.

**`eat:HospitalService` is the join the graph must keep.** Cardiology at 9001 is not
cardiology at 9002 — different staff, different waiting list, different beds. Every bed
and slot question hangs off it. Without it, "how full are the cardiology beds for this
patient" silently aggregates across every hospital and returns a plausible, meaningless
number.

## 3. Data-layer properties

**Amended (chore/ontology-literal-properties, 2026-09-03).** The original table below
covered relationships between nodes almost exclusively — outside `validFrom`/`validTo`,
almost no table's own attribute columns (names, dates, counts, flags) had a property at
all, which meant the data layer could not state most of what each source table actually
records. This amendment adds one property per such column, audited against
`dataset/DATASET_README.md` §7 and the live Postgres schema. Two rules governed the audit:
a column already covered by an existing relationship, a dedicated event node, or the Type-2
change-detection view is not restated (e.g. `removal_date` stays `eat:validTo`, and
`last_cancellation_date`/`suspension_start_date`/`suspension_end_date` on `referral_daily`
are not restated on `eat:ReferralState` because `eat:CancellationEvent`/
`eat:SuspensionEvent` already carry the authoritative values); a column present in
`core.ref_codes` (confirmed live: `cancellation_reason`, `clinic_classification`,
`gp_priority`, `referral_source`, `removal_reason`, `suspension_reason`, `triage_category`,
`triage_outcome`) becomes an object property with range `skos:Concept` (or the dedicated
class, e.g. `eat:CPC`/`eat:TriageOutcome`, where one already exists), never a literal, per
requirements.md R6.

**`eat:referredToService` moves from `eat:Referral` to `eat:ReferralState`.**
`specialty_hipe` is one of requirements.md R1's material fields — it changes on redirect,
which is exactly what mints a new `eat:ReferralState`. Under decisions.md §1, "never-changing
fields sit on `eat:Referral`"; a field that can differ between one state and the next is not
one of them. See the track's `decisions.md` for the full reasoning.

**`eat:atHospital`'s domain is widened to include `eat:Ward`.** `eat:Ward` is
hospital-scoped by IRI convention (`ward/{hospital_hipe}/{ward_id}`) exactly like
`eat:Patient`, but had no triple stating which hospital it belongs to. Reusing the existing
property closes the gap without minting a new predicate that would mean the same thing.

**`sosa:hasSimpleResult` and `sosa:resultTime` were named as reused SOSA vocabulary in §1
but never given a domain/range refinement.** Without `hasSimpleResult` in particular, no
`sosa:Observation` individual has any way to state the value it measured — added here
alongside the refinements already present for `hasMember`/`observedProperty`/
`hasFeatureOfInterest`.

**`eat:SuspensionEvent` gains `time:hasTime` (OWL-Time, reused) linking it to a
`time:Interval`.** decisions.md is explicit that `adjusted_wait_days` is only derivable if
suspended periods are real intervals in the graph; without a property connecting the event
to a `time:Interval`, `suspension_start_date`/`suspension_end_date` would have nowhere to
attach.

statement.** One query gets the whole explanation; the same query with a sub-property gets
one section of the clinician's expander.

## 5. Observation subclasses

The three kinds the dataset keeps apart become subclasses of `sosa:ObservableProperty`:

| Subclass | Columns | Produced by |
|---|---|---|
| `eat:MeasuredVital` | `hr`, `sbp`, `dbp`, `rr`, `temp`, `spo2` | A machine or a nurse |
| `eat:ReportedSymptom` | `pain`, `chiefcomplaint` | The patient |
| `eat:ClinicalAssessment` | `avpu`, `news2`, `mts_category`, `icts_category` | Clinician, or arithmetic |

Clinicians keep measured and reported information strictly apart because one is evidence
and the other is testimony. The distinction must survive into the graph.

## 6. CPC ordering

Severity order lives in the graph, not in code:

```turtle
eat:CPCScheme a skos:ConceptScheme ;
    skos:prefLabel "Clinical Prioritisation Category" .

<…/kg/id/cpc/1> a skos:Concept ;      # Urgent
    skos:inScheme eat:CPCScheme ; skos:notation "1" ;
    eat:severityRank 1 ; eat:crtDays 28 .
<…/kg/id/cpc/3> a skos:Concept ;      # Semi-Urgent
    eat:severityRank 2 ; eat:crtDays 91 .
<…/kg/id/cpc/2> a skos:Concept ;      # Routine
    eat:severityRank 3 .              # no crtDays

eat:outranks a owl:ObjectProperty, owl:TransitiveProperty ;
    rdfs:domain eat:CPC ; rdfs:range eat:CPC .
<…/kg/id/cpc/1> eat:outranks <…/kg/id/cpc/3> , <…/kg/id/cpc/2> .
<…/kg/id/cpc/3> eat:outranks <…/kg/id/cpc/2> .
```

Note the code values: Urgent 1, Routine 2, Semi-Urgent **3**. Anything that sorts by
`code_value` puts Routine ahead of Semi-Urgent, silently. Use `eat:severityRank`.

## 7. Not in the graph

- **`eval.ground_truth`** — no triples, in any graph, under any circumstances. Enforced by
  the `kg_loader` role having no grant on schema `eval`.
- Names, addresses, phone numbers, emails — not in the dataset by design.
- GP and consultant identities — not stored. A ranking should not know whose patient it is.
